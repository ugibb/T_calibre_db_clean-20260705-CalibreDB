## 一、验证目标

确认 Step3 流水线（合并 + 回归扫描 + 清洗 SQL）的正确性：
- 不该删的没被删
- 该删的都删干净了
- 数据库内部无残留垃圾

---

## 二、验证分四层

### 第一层：cleaned.db 内部完整性

**目的**：cleaned.db 本身是否是一个合法的 Calibre 数据库？

| 检查项 | 查询逻辑 | 预期 |
|--------|---------|------|
| 孤儿 data | `data.book` 不在 `books.id` 中 | 0 |
| 空 book | `books.id` 没有对应的 `data` 记录 | 0 |
| 孤儿 link | link 表（books_tags_link、books_custom_column_1_link 等）的 `book` 不在 `books.id` 中 | 0 |
| 重复 format | 同一 `book` 出现相同 `format` 的 data 记录 | 0 |

**说明**：
- 孤儿 link 是最容易出问题的地方。合并时如果 link 表清理不完整，会残留大量指向已删除 book 的记录。
- 空 book 说明清洗 SQL 的「删除空 book」逻辑有遗漏。

---

### 第二层：cleaned.db 删除正确性

**目的**：确认 cleaned.db 的删除结果完全符合预期，没有多删也没有少删。

| 检查项 | 逻辑 | 预期 |
|--------|------|------|
| 无新增 | cleaned 的 book/data 集合 ⊆ merged 的集合 | 无意外新增 |
| 删除数量一致 | merged → cleaned 实际删除数 = SQL 中 DELETE 语句数 | 完全一致 |
| 空 book 已清除 | cleaned.db 中不存在没有 data 记录的 book | 0 |

**说明**：
- cleaned.db 应该是 merged.db 的严格子集（只减不增）。如果 cleaned 的 books/data 数量比 merged 多，说明 cleaned.db 是旧文件残留，没有被正确覆盖。
- 合并步骤未来计划移除，届时 cleaned.db 直接由 input DB 经清洗 SQL 生成，验证逻辑不变。

---

### 第三层：CSV ↔ SQL ↔ DB 一致性

**目的**：确认 CSV 里的决策被 SQL 正确翻译，SQL 被正确执行。

| 检查项 | 逻辑 |
|--------|------|
| CSV delete → SQL DELETE | CSV 中 `recommended_action=delete` 的 data_id，在 SQL 中都有对应 `DELETE FROM data WHERE id = X` |
| SQL DELETE → 实际执行 | SQL 中的 DELETE 语句在 cleaned.db 中确实生效（对应 id 不存在） |
| book 删除条件 | 只有当 book 的所有 data 都被删时，才出现 `DELETE FROM books` |

**说明**：
- 这一层确保「决策 → 指令 → 执行」三环节没有信息丢失。
- book 删除是条件删除（`AND NOT EXISTS (SELECT 1 FROM data WHERE book = X)`），需要验证条件判断正确。

---

### 第四层：物理文件一致性（Windows 侧验证）

**目的**：BAT 执行后，文件系统与 DB 一致。

| 检查项 | 逻辑 |
|--------|------|
| data → 文件存在 | cleaned.db 每条 data 记录，对应物理文件存在于 winner 目录下 |
| 删除 → 进隔离区 | CSV 标记 delete 的文件，应从库目录移到 quarantine |
| 合并 → 文件到位 | loser 目录中互补格式的文件，应移到 winner 目录 |

**说明**：
- 这层只能在 Windows 上跑 BAT 之后才能验证。
- 物理文件路径 = `books.path` + `data.name` + `.` + `data.format.lower()`。
- 合并后 data 记录的 `book` 指向 winner，但物理文件可能还在 loser 目录下（等 BAT 移动）。

### 核心查询

#### 第一层：内部完整性

```sql
-- 孤儿 data
SELECT COUNT(*) FROM data WHERE book NOT IN (SELECT id FROM books);

-- 空 book
SELECT COUNT(*) FROM books WHERE id NOT IN (SELECT DISTINCT book FROM data);

-- 孤儿 link（对每张 link 表执行）
SELECT COUNT(*) FROM books_tags_link WHERE book NOT IN (SELECT id FROM books);
-- ... 其他 link 表同理

-- 重复 format
SELECT book, format, COUNT(*) as cnt
FROM data
GROUP BY book, format
HAVING cnt > 1;
```

#### 第二层：删除正确性

```python
# 在 Python 中对比两个 DB 的 id 集合
merged_books = set(query(merged_db, "SELECT id FROM books"))
cleaned_books = set(query(cleaned_db, "SELECT id FROM books"))
removed_books = merged_books - cleaned_books
added_books = cleaned_books - merged_books  # 应为空集
```

#### 第三层：CSV ↔ SQL 一致性

```python
# 从 CSV 提取 delete 的 data_id
csv_delete_ids = {row['data_id'] for row in csv if row['recommended_action'] == 'delete'}

# 从 SQL 提取 DELETE 的 data_id
sql_delete_ids = {int(match.group(1)) for line in sql for match in [DELETE_DATA_RE.match(line)] if match}

# 对比
assert csv_delete_ids == sql_delete_ids, "CSV 与 SQL 不一致"

# 验证 SQL 已执行
for data_id in sql_delete_ids:
    assert not exists_in(cleaned_db, "data", data_id), f"data_id {data_id} 未被删除"
```

## 四、已知问题（已修复）

### 问题 1：link 表孤儿清理不完整（已修复）

**根因**：step1_dedup.py 和 step2_anomaly.py 删除 books 时没有清理对应的 link 表记录。

**修复**：
- `common.py` 新增 `cleanup_orphan_link_records()` 共享函数
- `step1_dedup.py`、`step2_anomaly.py` 删除 books 后调用该函数
- `step4_sql.py` 的 cleaning SQL 末尾追加 `DELETE FROM link_table WHERE book NOT IN (SELECT id FROM books)`
- 验证结果：cleaned.db 所有 link 表孤儿数 = 0

### 问题 2：cleaned.db 旧文件残留（已修复）

**根因**：`shutil.copy2` 前未删除旧文件。

**修复**：`step4_apply.py` 在 copy 前先 `cleaned_db.unlink()`。

### 问题 3：空 book 未被清洗（已修复）

**根因**：cleaning SQL 只删除「因 data 全删而变空的 book」，不处理原本就没有 data 的 book。

**修复**：`step4_sql.py` 的 `_build_sql()` 增加 `_pre_existing_empty_books()` 查询，将原本就空的 book 也加入删除列表。
